# Generating Three-Address Code and Performing Liveness Analysis
This is a tutorial on how to generate three-address code (TAC) from an AST and perform liveness analysis on the temporaries generated by the TAC.
The motivation behind this tutorial and its contents is part of my independent study in building a compiler that compiles custom programs to PTX -*Parallel Thread Execution (PTX) is Nvidia's low-level virtual machine and ISA acting as a stable IR for CUDA*-.
This tutorial is a continuation of this series, and is the logical next step after the previous tutorial about writing a parser and AST for the compiler's domain specific language (DSL). The ultimate goal, as stated in previous tutorials, is to execute custom fatbin files generated by my compiler using the Nvidia Driver API.

All files this tutorial refers to will be in the ~/2ptx-compiler/ directory.

## Converting the AST nodes to Three-Address Code
The first part of this tutorial is converting AST nodes to lines of TAC. Due to the lack of control flow in the DSL, the phi functions necessary for true static single assignment (SSA) are not necessary in making the intermediate representation (IR) of this language SSA compliant. If control flow was added to the language via if-statements, phi functions would become necessary.

The first step is to create classes for each of the TAC formats/derived classes. All the code mentioned for this step will be in ```tac_nodes.hpp```. The base class is ```TACNode```, and only contains the default constructor, ```virtual``` destructor, and a ```to_string()``` class method. The base class destructor should almost always be declared virtual to ensure proper cleaup of resources when deleting a derived class oject through a base class pointer. Now that the base class exists, derived classes can inherit the base class. When reasoning about what types of TACs should be derived from TACNode, it is easiest to look at the AST node classes. Most of the AST nodes require a match to a TACNode, such that crucial language information derived and stored in the AST won't be lost when translating to the TAC. For that reason, in this implementation there are four derived classes: ```TACConstant``` corresponds with ```Integer```, ```TACBinaryOp``` corresponds with ```ArithmeticExpression```, ```TACStore``` corresponds with ```AssignmentExpression```, and ```TACLoad``` corresponds with ```Variable```. The contents of the classes themselves are pretty barebones, with a constructor using a initializer list and a implementation for the ```to_string()``` class method. 

The second step is actually converting the AST nodes to TAC. All the code for this step will be in ```ast.hpp```. Starting with the base class ```Expression```, new data structures and variables have to be defined to keep track of the parts for the TAC. An integer ```int temp_counter = 0``` keeps track of the number of temporaries in the the code. Using a counter also makes it easy to name future temporaries as well. 
```
static inline std::vector<std::unique_ptr<TACNode>> tac_nodes;
```
stores the ```TACNode``` instances in a vector. Another useful data structure implemented in this project is 
```
static inline std::unordered_map<std::string, int> expr_to_temp;
```
which stores assigned values to remove redundancy. The use for ```expr_to_temp``` is as follows: 
1. check if ```expr_to_temp.find(key)``` returns a value or past-the-end iterator.
2. If the value already exists, assign the variable ```temp_id = it->second``` and return. This means that the current node being evaluated has the same value as a previous temp, so the node's ```temp_id``` variable stores the value.

The above described data structures and variable are all declared static because they belong to the class itself, not the instances. It allows for those values to exist for the lifetime of the program, which is necessary for counters and data structures storing outputs from multiple instances of the derived nodes from the AST. 

Moving on, the most important method in the classes ```Integer```, ```ArithmeticExpression```, ```Variable```, and ```AssignmentExpression``` is the ```void three_address_code()``` method, which as the name suggests, generates the appropriate ```TACNode``` for that AST node. Generally, the methods:
1. Check if the value of the AST already exists as a temp.
2. Either assign an exisiting temp number to the ```temp_id``` variable or create a new temp with ```Expression::new_temp()```
3. If creating a new temp, make a ```unique_ptr``` of the corresponding derived class of ```TACNode``` with the necessary arguments, and add the new TAC node to the vector storing results.
4. Add a new entry in the ```expr_to_temp``` map for the current expression's key and ```temp_id```.

The ```three_address_code()``` implementation for ```ExpressionList``` is unique because it is only
```
for (const auto& expr : expression_list) {
  expr->three_address_code(); 
}
```
```ExpressionList``` doesn't create new ```TACNode```'s like the other AST nodes, because its use in the AST is as a parent of nodes which produce temporaries. 

The ```Vector``` implementation is incomplete at the time of writing the current iteration of this tutorial. 

For more specific implementation details, check out the ```ast.hpp``` file, and look at the overrided method implementations for ```three_address_code()```. 

## Performing Liveness Analysis on TAC Nodes
Performing liveness analysis is a crucial step in compilers because it gathers information necessary to conduct register allocation. Register allocation will be explained in further detail in the next section. Liveness analysis is the step of a compiler where the lifetimes of all temporaries are determined. A lifetime/live range of a variable (when I say variable here I mean it in the most vague way) means that a variable v is live at point p if it has been defined along a path from the procedure's entry to p and there exist a path from p to a use of v along which v is not redefined. Knowing live ranges of variables allows the register allocation algorithm to determine which temporaries (temporaries are the temporary variables the TAC generates per line) to remove from the set of temporaries and add to the set. This is important because the algorithm (and compiler in general) is often allocating many temporaries to a few registers, and the algorithm prioritizes preventing register spills. 

All the code for liveness analysis will be found in ```/2ptx-compiler/liveness_analysis.hpp```

The first thing to do is to define some structs. ```LivenessInfo``` and ```LiveRange``` are two important structs for the ```LivenessAnalysis``` class. ```LivenessInfo``` stores the temps that are live before an three-address code instruction executes, and also stores the temps that are live after a three-address code instruction executes. These are equivalent to what are called live-in and live-out sets in compiler textbooks. Since we made temps type ```int``` in our compiler, storing temps is simple. Just save what number the temp is. The other important struct is ```LiveRange```, which stores the start instruction number and the end instruction number for a specific temp. These are used as values in a ```std::unordered_map<int, LiveRange>``` to store the live ranges of each temp. This data structure will be used as a argument to a register allocation function. 

```
struct LivenessInfo {
    std::set<int> live_before; 
    std::set<int> live_after; 
    std::set<std::string> live_var_before; 
    std::set<std::string> live_var_after; 
};

struct LiveRange {
    int start; 
    int end; 
};
```

On to the ```class LivenessAnalysis```. The public member variables necessary are
```
std::unordered_map<int, LiveRange> temp_to_live_range;
std::unordered_map<std::string, LiveRange> var_to_live_range; 
std::vector<LivenessInfo> instruction_liveness; 
std::unordered_map<std::string, int> var_def_index;
```
The live range ```unordered_map``` variables keep track of the live ranges of the temporaries and variables that live in the three-address code. ```instruction_liveness``` is a vector of ```LivenessInfo```, and it contains liveness at each instruction i (all the temporaries that are live at each instruction). 

As the reader may notice, there are some variables that keep track of three-address code variables. The liveness / live ranges of variables in the three-address code are somewhat trivial because variables are live for the lifetime of the program in memory, and thus the living model is different from the liveness of temporaries. These data structures are still used in register allocation, but only to keep track of how many variables exist. Someone following along these tutorials may find a more efficient and elegant way to store information on variables without gathering live ranges. This specific implementation may be modified in the near future. 

There are no private member variables, but there are some private class methods. ```get_definition()``` takes a three-address code as input, and then adds every definition of a temporary to the ```std::vector<int> defs``` vector. In this context, definition of a temporary refers to a instance where a new temporary is created in the tac instruction. In the 2ptx-compiler, the three-address code instructions that define temporaries are ```TACConstant```, ```TACBinary```, and ```TACLoad```. ```TACConstant``` and ```TACLoad``` only define temporaries, and will never use a temporary on the right-hand side. For the reader, use ```dynamic_cast<*>()```, a dynamic cast of a instruction into a tac node pointer, for each tac node. It allows for variable assignment and type-checking in one action. 

```get_uses()``` takes a three-address code as input, and then adds every use of a temporary to the ```std::vector<int> uses``` vector. It is the opposite of ```get_definition()```. The uses for a temporary are either operands (rvalues) in ```TACBinary```, or the temporary getting stored in memory with ```TACStore```. 

Implementing these two helper functions is crucial for liveness analysis, because the result of these functions will be used to modify the live set (temporaries that are live at each instruction). 

Next, implement the public class method ```analyze(const std::vector<std::unique_ptr<TACNode>>& tac_instructions)``` which takes a vector of unique pointers for ```TACNode``` instructions. The trickiest part of the implementation for this function is the logic for the reverse linear scan liveness analysis, which is a simple and efficient backwards dataflow analysis algorithm. First, declare the set ```std::set<int> live_set``` which will temporarily hold all the temporaries that are live for the lifetime of the liveness analysis pass. When writing the for loop, make sure the loop iterates from the last tac node instruction to the first. For each instruction, first
```
instruction_liveness[i].live_after = live_set
```
meaning, set the liveness of temporaries after the current instruction executes to the live set from the previous instruction (the instruction that executes after the current one, imagining normal order). Next, get the definitions and uses at this instruction using the ```get_definition()```, ```get_uses()``` helper functions, explained earlier in the tutorial. Using the defs and uses that the algorithm just returned, remove all definitions from the live set by looping through ```std::vector<int> defs``` and removing the elements in ```def``` from the live set. Definitions at instruction i will not be referenced anywhere above, because the chain starts at the definition, so the temporary will never show up in a line above. For the ```std::vector<int> uses```, insert all the uses into the live set, as they are still live. A use at instruction i means there are potentially more uses in earlier lines, and definitely a definition above. At the end of each loop, set the liveness before the instruction executes to the current live set, after the definitions get removed and the uses are added: ```instruction_liveness[i].live_before = live_set```.

After the for loop, compute the live ranges with a helper function. ```compute_live_ranges()``` is a private helper that iterates through all the instruction ```LivenessInfo``` instances. For both the instruction live before and live after sets:
```
if (first_use.find(temp) == first_use.end()) {
  first_use[temp] = i; 
}
last_use[temp] = i;
```
If the temp is being defined for the first time, meaning there are no defs nor uses previously (```first_use.end()```), set the first occurrence of this temp, ```first_use[temp]``` to i. If the temporary has already been seen for the first time, update the ```last_use[temp]``` to be i. Finally, populate ```std::unordered_map<int, LiveRange> temp_to_live_range``` and return.
